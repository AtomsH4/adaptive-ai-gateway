# 向生产规格演进的阶段门槛

修订：2026-11-09。这里给出发布条件与迁移顺序，不将当前架构基础或模拟测试称为生产可用。

## 1. 保持初版简单的理由

单机本地模式先使用模块化单体、一个协调器和一个受管模型。数据面协议、资源账本与后端实现分开，因此之后能够替换平台、引擎、入口和部署形态。预先引入消息总线、Kubernetes 或分布式数据库并不能代替取消证据、未知占用与正确的并发记账。

## 2. 分阶段门槛

| 阶段 | 应增加的能力 | 发布或升级前的证据 | 当前状态 |
| --- | --- | --- | --- |
| A：架构基础 | 依赖边界、领域值、消费方端口、机器可读契约、替换与反例测试 | `make check`、`make contracts`、要求到证据的审计 | 已完成基础门槛 |
| B：可用本机版本 | T0–T8 的 HTTP、调度、真实引擎与 Python 闭环 | 固定模型/引擎、真实取消和卸载、日常应用对照测量 | 已有控制原型；T6/T8 尚未验收 |
| C：可靠单机服务 | 所有权 journal、重启对账、密钥更新、受控关闭、配置代次与运行观测 | 崩溃/重放/磁盘损坏/断流故障注入；长期运行与升级回滚记录 | 后续发布阶段 |
| D：受控远程 Worker | 鉴权与加密 RPC、Worker 本地资源所有权、命令去重与 fencing、持久化协调状态 | 网络分区、重复命令、过期租约与旧所有者测试均不超发 | 有明确多机需求后 |
| E：生产集群与团队治理 | 容量规划、租户配额、HA、滚动升级、备份恢复与运维响应 | 按真实流量与 SLO 验收，明确恢复目标和责任人 | 不属于当前实现承诺 |

前一阶段未通过，不用后一阶段的组件包装成已经可靠。新增数据库或总线时增加对应端口与独立迁移任务，保持领域规则与公共 HTTP 契约可复用。

## 3. 可靠单机的初始验收方案

以下数值是后续工程门槛候选，必须在受测机型和负载上核验，不能当作已达成绩效：

- 固定配置连续运行至少 4 小时，并累计至少 1000 个合法调用；记录每类成功、拒绝、取消和不完整结果，不用“资源拒绝符合预期”把它从用户可用性中隐藏。
- 至少 100 轮受控启动/关闭与取消场景，确认所有可证明归属的受管进程按预算回收；强杀与崩溃恢复单独验证，不把受控关闭结果外推到 SIGKILL。
- 不含模型执行、加载或排队的控制路径，先以额外 p95 开销低于 10 ms 为目标；报告测量边界和负载，而不是将快速 healthz 当作推理低延迟。
- 不能确认执行结束时不重新分配槽位；旧实例、重复命令、journal 损坏与磁盘写入失败都应保持容量保守。
- 验证日志、诊断和指标不包含 token 密钥及原始聊天内容，输出缓冲、事件记录和标签数量在持续负载下有上限。

CPU、GPU 与模型吞吐没有统一生产阈值，应按具体机型和服务模型设独立的预算、配置与容量报告。

## 4. 可靠性与持久化边界

内存队列不跨进程重启保留请求。首版连接断开后不能自动续接正在生成的回答；未来若提供任务查询或恢复，须新增显式协议、保留周期和状态持久化，而不是假设现有 request ID 就是幂等键。

可靠单机阶段在副作用之前记录最小操作意图和所有者，完成后记录证据及结果。journal 不存原始 prompt 或 response；损坏或缺失时先对账，不能当作空账本重新加载第二份模型。只有需要持久化后，才设计存储端口，避免提前引入通用 Repository。

租约与 fencing 可以阻止过期所有者提交新命令，但不能证明旧 GPU 工作已经停止。网络分区、Worker 失联或租约到期后仍需执行停止证据或保守隔离；这是远程 Worker 的准入门槛，不是通过一个 Redis 锁即可解决的问题。

## 5. 安全与配置演进

本机默认 loopback 和单个本地 Bearer 令牌。未来开启非本机监听前，必须配置 TLS、身份验证、独立的运维面访问策略与请求限额，并通过集成测试；不自动将本机开发配置暴露到公网。

后端和模型来源按版本及摘要锁定。下载先写临时文件，验证完整性后再原子发布；缓存损坏或摘要不匹配时不执行文件。启动参数使用参数数组，不把模型 ID、路径或请求内容拼接为 shell 命令。

配置与模型 profile 有版本；运行中的请求绑定接受时的模型身份、配置和规则代次。热更新先校验再发布新的不可变快照，影响实例参数的变更在排空后建立新代次，不能偷偷改变在途请求的上下文上限。

## 6. 可观察性不掌握控制权

资源压力、队列、加载和执行时间使用独立指标；request ID、错误明细进入有界日志或追踪，不能直接作为指标标签。模型、后端、结果等标签需有受控集合与数量上限，避免标签组合造成无界内存，参见 [Prometheus 指标建议](https://prometheus.io/docs/practices/instrumentation/#do-not-overuse-labels) 与 [OpenTelemetry 内存指南](https://opentelemetry.io/docs/specs/otel/metrics/supplementary-guidelines/#memory-management)。

日志和指标输出故障不得卡住容量回收。可丢弃的观测事件采用有界通道与丢弃计数；不可丢弃的业务证据仍由协调器和后续 journal 管理，不能混进同一个“最佳努力事件总线”。

## 7. 对外兼容与升级

机器可读 HTTP 契约用于校验和版本对比。新增可选响应字段可兼容扩展；删除字段、改变错误/流结束语义或改变鉴权要求，需要显式版本策略和迁移说明。Python 调用方容忍新字段和未知错误码，但未知错误不能变成成功。

接口版本、后端协议版本、模型修订和配置版本分别记录，不能使用一个版本号代替所有兼容性。构建、依赖与模型清单可追溯后再发布；升级前验证旧配置读取、排空和回滚，版本回退不会删除未知占用记录。
